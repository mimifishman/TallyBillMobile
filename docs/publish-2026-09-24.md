## Receipt scanning (server)

### 1. Discounts on US receipts are now read — the 1.1.0 blockers

Before this, two common ways US restaurants print a discount were ignored, and the
bill came out **too high**.

| How the receipt prints it | Before | Now (dev, 3+ runs each) |
|---|---|---|
| A minus line under the item — `DRAFT IPA 16.00` / `HAPPY HOUR 50% -8.00` (Square, Toast) | 8.00 too high, every time | **right 11/12 as a phone photo** — the 12th kept the warning |
| One discount for the whole bill at the bottom — `Industry Night (15%) -15.60` (Square) | 15.60 too high, every time | **right, 3/3** |
| A `COMP` line under the item (Aloha) | right with the new crop | still right |
| Happy-hour prices with no discount line (Toast) | right | still right — no discount is invented |

**Why they failed, and the fixes:**

- **Discount under the item.** The main model (gpt-4o) often ignores the minus
  line. Now, only when the items come to *more* than the receipt's own printed
  total, a second model is asked to read the same photo. Its answer is used only if
  it adds up to that same printed total, describes the same items at the same full
  prices, and only lowers the bill through discounts. Tax, tip and currency always
  come from the main model. *(PRs #81, #82, #83, #88)*
- **Discount at the bottom.** The model read the 15.60 correctly, but reported the
  total **with tax** (96.25) as the receipt's total, so our check threw the
  discount away. The check now allows for tax added on top:
  104.00 − 15.60 + 7.85 = 96.25. *(PR #82)*

### 2. Photos framed tight on the items no longer lose lines

The scanner cuts off the top quarter of every photo, to drop the shop's name and
address. On a photo that starts at the first item, that cut **took real items** —
a US receipt came back with 2 of its 8 lines, and your Hebrew 306 photo lost its
first three.

**Fix:** when a cut happened *and* the items come to **less** than the printed
total, the whole photo is read again and the reading closer to the receipt wins.
Both tight test photos now come back complete. *(PRs #86, #87)*

**Why not just remove the cut:** it was measured again today. Without it, Hebrew
totals fell from **21/21 to 12/21**. The cut is essential for Hebrew, so it stays.
*(PR #87)*

### 3. Hebrew receipts are protected from the discount backup

On one Hebrew receipt the main model read every item right but took the
card-machine slip underneath (90.00) as the total, so the backup was asked every
time — making that scan **19 seconds instead of 8**, for nothing. The backup now
only runs when the gap looks like a missed discount (items too high by at most
half the bill). *(PR #82)*

### 4. The models

| Job | Model | When |
|---|---|---|
| Read every receipt | **gpt-4o** | every scan |
| Read the whole photo again | **gpt-4o** | only when lines went missing |
| Discount backup | **gpt-5.4** | only when items come to more than the printed total |
| Translate button | gpt-4o | when pressed |

- **o4-mini is no longer used.** Replit is retiring it. It was the first discount
  backup and was replaced by gpt-5.4 after testing: 11/12 right and 10.5–12s,
  against Replit's suggested gpt-5.4-mini at 9/12. *(PRs #84, #85)*
- **gpt-5.4 was tried as the main reader and taken back out the same day.** It
  reads Hebrew item names much better, but on a tight photo of a real Hebrew
  receipt it **made up a printed total** that matched its own items. That silently
  turns off every safety check, and it undercharged by 45.00 with no warning, 3
  times in 6. gpt-4o got the same photo right every time. *(PRs #89, #90)*
- **Watch out:** gpt-4o is not on Replit's retirement list yet, but it is older
  than gpt-4.1, which is.

### 5. Time

Scans stay inside the 20-second limit on every test receipt. The slowest cases are
the ones that need a second read — a tight photo, or a US item-level discount — at
about 11–17 seconds. The backup and the re-read both stop at a hard deadline and
fall back to the first reading rather than run over.

## Behind the scenes — how this was tested

- **New test receipts:** four US discount layouts (another session) and five clean
  Hebrew receipts, each hiding one known trap. Printable copies are in
  `app_screenshots/v1.1/hebrew/`. *(PRs #70, #88)*
- **The test tool now:** reads photos the same way the real scanner does, scores
  bill-level discounts, scores Hebrew names on all seven real Hebrew receipts, adds
  a "close enough to recognise" name score, and reports each model separately.
  *(PRs #70, #78, #79, #80)*
- **Model tooling:** the model is a setting, not code, and new models can be tried
  on dev without a code change. Models that refuse `temperature: 0` or run out of
  room while "thinking" are no longer mistaken for missing ones.
  *(PRs #74, #75, #76)*
- **Every API response says which code it is running** (`X-Build-Commit` header),
  so "is dev up to date?" is one check instead of a guess. *(PR #77)*
- **Taken back out, on the record:** reading a quantity from an item's name
  ("Pork Dumplings x 2"), because "Chicken Wings x 10" is one dish, not ten; and two
  discount prompt rules that broke English. *(PR #70)*
